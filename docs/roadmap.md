# Gurdy — Build Roadmap (public)

**Baseline:** `docs/spec.md` (normative; this document sequences it, it does not
amend it).

The build track: what is done, what is left, and the debt inside what exists.
Commercial sequencing — phases 3 and 4, the non-code track, and the open
business questions — is tracked separately and is not published.

## 1. Where the build actually is

Against §8.2, **Stages A–E are built, tested, and green** (`go test ./...` passes; ~3,000 lines across 20 files, roughly 40% of it tests):

| Built | Where |
|---|---|
| Pass-through HTTP proxy + stdio shim; MCP `tools/call` parsing incl. JSON-RPC batch | `cmd/gurdy-proxy/`, `internal/mcp` |
| TIS: ES256 mint/derive/verify, narrow-only scope algebra, jti replay cache, audience binding | `internal/tis` |
| Cedar PDP, `@id` re-keying, case-normalized tool matching, embedded starter policies | `internal/policy` |
| Hash-chained JSONL ledger, ES256 batch signatures, bounded queue with drop counter | `internal/ledger/ledger.go` |
| Offline verifier — the Stage D independence test | `cmd/gurdy-verify/`, `internal/ledger/verify.go` |
| Bundle load / hot-reload / rollback; localhost admin API with CSRF guard | `internal/bundle`, `internal/policy/store.go` |
| OTel decision spans joining the agent's trace | `cmd/gurdy-proxy/main.go` |

That is the deepest and smallest part of the system. `sdk/`, `conformance/`, and `cloud/` are still empty. Roughly 60–70% of Phase 1 remains.

## 2. Debt inside the built code

Verified against the source, ordered by how much downstream work each blocks.

| # | Item | Location | Why it matters |
|---|---|---|---|
| ~~D1~~ | ~~**No mint surface**~~ | — | **DONE** 2026-07-25. `POST /mint` + `POST /derive` on a Unix socket (`<state-dir>/tis.sock`, owner-only), separate from the admin API and from the reverse-proxy path, with no `/derive-call`. The SDK track is unblocked; what remains for the SDKs is their own work (§3.F), not a missing proxy surface |
| ~~D2~~ | ~~**TIS keypair is ephemeral per process**~~ | — | **DONE.** Both keys now load from `-state-dir` via `internal/keyfile`. Copying `ledger.loadOrCreateKey` first meant reading it, which surfaced two things it was getting wrong: the ledger's **private key was being written into the ledger dir — the export you hand an auditor**, and a plain create let two processes each keep a different key. Persisting the key also *removed* a replay defense that was holding by accident (see §3.B) |
| ~~D3~~ | ~~**Ledger partition hardcoded `"default"`**~~ | — | **DONE.** `-tenant` flag; partition = tenant + attested-coarse workload. Not the two-line change it looked like: real partition names carry `:` and `/` and arbitrary case, so `url.PathEscape` had to be replaced with a hashed filename encoding (case-insensitive filesystems would otherwise merge two workloads into one chain), and per-workload files needed an fd budget with LRU eviction — a monitor proxy that exhausts fds stops governing (NFR-3) |
| ~~D4~~ | ~~**Response capture**~~ | — | **DONE.** HTTP landed with v0.8.2; the stdio half landed 2026-07-25 with v0.8.6. The correlation problem was the whole delay, and it was resolved by *refusing* every ambiguous case rather than solving it: an id with more than one call outstanding, a `null` id, an oversized id, an unparseable frame, or a pending map past its bound all leave the call **unanswered** — a visible missing half — instead of a guessed `call_id` no reader could detect as wrong. Review found four variants of one bug in the first version (*state that outlives its own proof*), all now regression-tested. Stdio correlates per batch *element*, finer than HTTP's shared envelope hash. `classification` remains unimplemented and belongs with the packs |
| D13 | **Response hashing is per-byte and uncapped** | `cmd/gurdy-proxy/main.go` (`hashingWriter`) | The request body stops being inspected past `maxInspect`; a *response* is hashed however large it is, because a partial hash is evidence of nothing. Measured at ~2.1 GB/s — **~0.45µs per KiB**, so ~2µs for a typical MCP reply and **~3ms for an 8 MB one**, most of the NFR-1 p99 budget on its own. Time-to-first-byte is unaffected (the client is written to before the hash), so what grows is total transfer time. No fix implied: the alternative is either no response evidence or a size cap that makes `resp_hash` mean "some of the response", which is worse than a slow big download. Named so the cost is a known property rather than a surprise |
| D14 | **The ledger has no rotation, retention, or compaction — one file grows without bound** | `internal/ledger/ledger.go` | **Schema + verifier landed 2026-08-10 (spec v0.8.7); the roller and the pruner are what remain.** The reader shipped first on purpose: a verifier that meets an unannounced segment rejects it as `gap or splice` and strands the whole export — confirmed by mutation, a legitimate segment 2 fails with `record 1: seq 6 after 0` against a verifier without the change. The header now carries `segment`; a continuation's `prev_hash` is the previous segment's last-line hash, so the seam is the ordinary chain link and there is no second field to disagree with it. `kind=retention` declares deliberate removal (`pruned_through_seq`/`_hash`, signed), so **silent deletion fails verification and declared deletion is auditable** — author decision 2026-08-10: Gurdy may delete its own evidence, but only declared and signed. **Roller + cross-file verification landed 2026-08-10 (part two).** Partitions roll at **256 MiB** (~4 min at rated load), sealing before they close — a rolled segment leaves nothing unsigned, because the next process resumes the *latest* segment and those lines would otherwise sit outside every signature forever, appendable by anyone with file access. Resume continues the last segment rather than segment 1, which would fork the chain into two files both claiming the same successor. `gurdy-verify` groups segments by what the **headers** say (tenant/workload/instance) and orders by `segment`, never by filename — a filename is unsigned, so ordering evidence by one would let a rename reorder a chain. It reports a wrong predecessor, a missing middle, a fork, and a chain that begins mid-stream, and **only the last of those is excused by a retention record** — which is the whole distinction between authorised pruning and someone supplying the part that suits them. **Pruner landed 2026-08-10 (part three), operator-invoked only** (author decision): `POST /retention/prune?keep=N` on the admin API. No timer, no max-age setting, no background sweep — an evidence product that deletes its own records on a schedule is a different proposition from one that does it when asked, and the signed record makes either auditable without making both defensible. It lives on the admin API because the running proxy is the only thing that can do it safely: it holds the signing key, the open chain, and the writer goroutine the append must be serialized against. **Record before effect**, the same ordering §5.5 demands of an enforced decision — the declaration is appended, signed and synced *before* any file is unlinked, so a crash in between leaves a chain that over-declares (verifies fine) rather than one with an undeclared hole (fails, and rightly). Whole segments only; pruning within a segment would mean rewriting a hash chain around the hole. **The seam check needed a fix this exposed**: it excused a missing beginning only if the *first surviving* segment declared the prune, but the pruner appends to the *current* one, so every real prune would have failed verification — and the declaration must now also **cover** the gap it excuses, since a record pruning through seq 40 says nothing about a chain starting at seq 900. `SECURITY.md` records that this widens the admin surface from "disarm the proxy" to "disarm it and delete evidence" — not worse in kind, worse in degree. **Free-tier boundary (author decision 2026-08-10): pruning is free and manual; retention *policy* — scheduling, per-tenant rules, fleet-wide application — is `gurdy-fleet`.** The capability is free, the coordination is paid, exactly as ADR-14 draws it for enforcement, and the manual step is deliberate friction. Recorded in §5.8's tier bullets because the paid list already said "retention" and could have been read as claiming the whole thing. Remaining: a `-ledger-max-segment` flag if 256 MiB turns out wrong for someone. Original finding: At NFR-2's rated 1,000 req/s the export grew **1.9 GB in 30 minutes — ~65 MB/min, ~92 GB/day** — as a single `.jsonl` per partition that is only ever appended to. 3.66M records for 1.8M calls (2.03 per call: decision + response, as designed), ~560 bytes each. **Append latency did *not* degrade as the file grew**, so this is a capacity problem and not a performance one. It is also not simply "add logrotate": the file *is* the chain, `prev_hash` links every line to the previous one, and the header names the pubkey for the whole file — so a rotation scheme has to say how a verifier walks across the seam, and a compaction scheme has to explain what a hash chain with a hole in it proves. Blocks any deployment expected to run for days, which is every real one |
| ~~D12~~ | ~~**`autoMint` holds a process-wide mutex across an ES256 verify**~~ | — | **DONE** 2026-08-15. The cached expiry is now read under an `RWMutex` read lock and compared against the clock; the ES256 verify is gone from the hot path. Re-verifying was never buying anything: we minted that token ourselves and never let it out of memory, so the only claim `VerifyTxn` could refute is expiry, and expiry is a value we already had at mint time. **Measured A/B on one machine in one session, 3 runs each: 65,018 → 18,345 ns/op parallel, 3.55× faster, 407 → 332 allocations** (~15,400 → ~54,500 decisions/sec). `BenchmarkDecideCallParallelWithTxn` is the control — it does not touch `autoMint`, and at 23,973 → 23,974 ns/op it did not move, which is what makes the speedup attributable to the change rather than to the machine. **The renewal margin is the load-bearing part, and it is about evidence rather than latency:** a token handed out microseconds before expiry makes `DeriveCall` fail, and that call is recorded with empty txn fields plus an identity gap (§5.5), so the cached expiry is held one minute early. Ceiling named in a `ponytail:` comment — expiry is the only staleness this understands, so key rotation (NFR-5, §3.B, not built) must flush the map. **The SDK path is now the slower one** (23,973 against 18,345) because it still verifies a supplied txn on every call. That asymmetry is correct and is commented as such: a supplied token is the governed party's claim, presented on every request, and caching a verification result for it would turn one valid presentation into a standing pass — the forged-credential case in `conformance/cases/05` |
| D10 | **The SDKs' fail-open posture is untested under a real outage** | `sdk/python/src/gurdy/_task.py`, `sdk/typescript/src/task.ts` | `task()`/`spawn()` degrade to unenriched when the TIS is unreachable, which is right (NFR-3's posture on the SDK side) and unit-tested against a dead socket in both languages. What is not tested is a TIS that *hangs* — the 5s socket timeout is on the connect/read, so a wedged mint stalls the wrapped work for that long. Belongs with the performance gates (§3.G) |
| D11 | **Redirects on a governed call are refused, not re-evaluated** | `sdk/typescript/src/fetch.ts` | `Gurdy-Txn` is a custom header, so the Fetch standard does not strip it cross-origin the way it strips `Authorization`, and `fetch` gives no per-hop hook. A request carrying the credential is issued `redirect: "manual"`, which closes the leak but declines to follow a redirect the caller asked to follow. The complete fix is an undici interceptor applying the rules on every hop — also the only way to cover a client the SDK did not wrap. The proxy is a chokepoint and does not redirect, so this is a ceiling rather than a bug |
| D9 | **Coverage gate at 83.1%, §8 targets 85%** | `.github/workflows/ci.yml` | Ratchet, not a target. The gap is `cmd/gurdy-proxy` process wiring and error paths. Raised 82.7 → 82.8 on 2026-08-09 and → **83.1 on 2026-08-10** with rotation, pruning and the admin endpoint; this line said 82.8 until 2026-08-15, when D12's work read it and found it a ratchet behind `ci.yml`. Each raise has been the *whole* margin available. D12's five tests moved it not at all, and that is the expected result rather than a disappointment: `autoMint` was already executed by every test running `decideCall` without a txn, so the new tests assert **behaviour on lines that were already covered** — which is exactly the blind spot a line-coverage number has and the reason the mutation checks are the real gate. Closing the remaining 1.9 points means testing process wiring, not adding tests to packages that already have them |
| D5 | **Request body fully buffered before forwarding** (4MB cap) | `cmd/gurdy-proxy/main.go` (`ServeHTTP`) | Most likely thing to blow the NFR-1 budget, and currently unmeasured |
| ~~D6~~ | ~~**`autoTxn` and `ledger.parts` maps are unbounded**~~ | — | **DONE** 2026-08-15, in two halves that turned out not to be one fix. **`autoTxn`** fell out of D12 for three lines: caching the expiry gave the map a notion of a dead entry, and minting (once per principal per ~14 min) is the one place an O(n) sweep is affordable. **`ledger.parts`** was the subtler one, because fd eviction *already existed* and looked like it had solved this — it releases the handle but deliberately **keeps the chain state**, so the map still grew once per (tenant, workload) key ever seen. Keeping that state was never necessary, only cheaper: `part()` already rebuilds seq and head with `scanTail` whenever a name is missing, which is the identical path a restart takes and is therefore exercised constantly. `maxParts = 4096` now drops the coldest **closed** partition on insertion. Closed is the whole safety argument: `evictLRU` signs an open batch before releasing a handle, so `f == nil` implies fully signed and flushed — the invariant the tick and `Close` already relied on — while forgetting an entry that still holds a writer would strand an unsigned tail outside every signature, the exact hazard D14's seal-before-roll exists to prevent. **That guard is unreachable today and kept anyway**, and the mutation test says so: fd eviction keys on the same `used` clock, so the open set is always the most recently used and the coldest is never open. It becomes load-bearing the moment the fd policy stops being LRU, and the failure it prevents is silent |
| ~~D7~~ | ~~**Coverage gaps surface only as a shutdown log line**~~ | — | **DONE** (spec v0.8.3). `kind=coverage` records emitted by the ledger's *writer goroutine*, never the queue — the queue that drops a record cannot be the path that reports the drop. Gap records land in the partition that lost the evidence (drops, write errors, and the `identify()` failures that were counted nowhere); heartbeat/shutdown records land in a `_proxy` chain whose missing shutdown record is the crash signal. `/health` reports the same counters and flips to `degraded`. **OTel gap metrics are the one piece not built** — they need a meter provider that does not exist yet, and they are the ops path, not the evidence path |
| D8 | **`allow-all-monitor` pollutes every `policy_ids` on allow** | `internal/policy/starter.cedar` | Cosmetic, but it is noise inside the evidence record |

### B. TIS completion — unblocks the SDK track

- [x] **D1 — mint surface. Complete 2026-07-25.** §5.9 collapses "proxy surface vs. SDK-local": the SDK never holds signing keys and dev mode's embedded core *is* the proxy on that machine, so it is one contract in both modes. The framing was also wrong about the risk — the hole is not that mint is unauthenticated, it is that **asserted identity currently suppresses attested identity**, and that is fixable without solving mint auth at all.
  - [x] **Evidence split.** `identify()` discards the coarse principal whenever a valid `Gurdy-Txn` is present, and `decideCall` records one `principal` slot fed from `call.Subject` (`cmd/gurdy-proxy/main.go:378`), so anything that can mint erases the proxy-observed fact — §5.2 says attested *never degrades*. Redefine `principal`/`principal_tier` to always mean the attested observation; add `assertion_status` (absent/valid/invalid), `asserted_principal`, `asserted_scope`; rename `human_actor` → `asserted_human_actor`. `lineage[]` is asserted too — omit it unless `assertion_status=valid` rather than writing auto-minted lineage as if it came from an SDK
  - [x] **Cedar evaluates on the attested principal**, so `ledger.principal == policy.Input.Principal`. Asserted values reach policy as **reserved context keys only** (`context.asserted_principal`, `context.assertion_status`) — that is §5.9's "policies may require attestation" made real: trusting an agent-side claim becomes a visible, reviewable line in a pack, instead of being silently handed over as `principal` (today) or unavailable entirely
  - [x] **Reserved-context-key collision.** Landed early, ahead of the registry — extractor attrs using a reserved name are now *dropped*, not overwritten, because the dangerous case is a forged `asserted_principal` when no real one exists to overwrite it. `Evaluate` seeds `context.tool` then overlays `in.Context` (`internal/policy/policy.go:73`), so an extractor-chosen key named `tool` shadows the normalized one — the same dodge the lowercasing exists to prevent. **Not exploitable today** (`extract.Attrs` emits only `resource_path`/`resource_host`, both hardcoded) — it arms with the extractor registry in §3.D. Write reserved keys last and reject `tool`/`asserted_*`/`assertion_*` from extractors; land it *with* the registry at the latest
  - [x] **Strip `Gurdy-Txn` before forwarding upstream.** `ServeHTTP` reads it then hands the original request to the reverse proxy (`cmd/gurdy-proxy/main.go:326`), so the upstream MCP server receives a reusable bearer transaction token. Safe to fix: `TestPassThroughByteIdentical` asserts request *body* and *response* headers, not request headers
  - [x] **Sideband TIS API** — landed 2026-07-25. Root mint + child derive only. Not the admin API (§7's disarm row is already unmitigated; don't widen it) and not a reverse-proxy path carve-out. Unix socket in stdio/dev mode, where stdin/stdout are the protocol channel and `-stdio` starts no listener at all today. **No `/derive-call`** — the proxy already derives per-call assertions internally. Child derive is a spawn-time round trip, so §8.2's fan-out gate must measure the call hot path separately from the 20 spawn-time derivations
  - [x] **Mint stays unauthenticated in v1, deliberately** (shipped that way; the socket's owner-only file mode is the control, and the code comment names exactly when it stops being adequate) — §5.2 defines SDK context as *asserted*; gating it distributes a secret without changing what the record means, once the split above lands. `cnf` proof-of-possession waits for the SDK. **This is a Phase 2 enforce gate, not a Phase 1 one:** `MintTxn` accepts any root scope (`internal/tis/tis.go:87`) and only *child* derivation enforces narrow-only, so a prompt-injected agent can mint `scope=*`. Harmless while nothing blocks and no policy reads scope; an authorization bypass the moment either changes
  - [x] **§8.2's "contradictory SDK context vs proxy-observed is flagged" is not satisfiable in Phase 1** — now said so in §8.2 itself. `asserted_principal` and `principal` are different namespaces (`fetcher` vs `svc:127.0.0.1`) — there is no equality predicate. Only `assertion_status == invalid` is honestly detectable until scope reaches policy or real workload identity exists. Say so rather than shipping something that looks like it satisfies the requirement
  - Ordering: spec amendment → header strip → evidence split (ledger + gateway + policy input move together) → sideband API. **The first three are a coherent stopping point without the sideband API**
- [x] Persist the deployment keypair (D2). Call assertions are now audience-bound to `deployID#<instance nonce>`, not `deployID`. The old cross-replica/cross-restart replay defense rested on the key being ephemeral — a captured assertion failed the *signature* check elsewhere. With a durable shared key that check passes everywhere, so the instance had to move into the audience. Txn tokens carry no audience and stay deployment-portable, which is the point of D2
- [x] **JWKS on the admin API** (§5.2) — landed 2026-08-16. `GET /jwks`, public halves only, current key first, both keys throughout the overlap. It is the one admin route a third party has any reason to read and the only one that gives nothing away; the rest of that API can disarm the proxy, which is the argument for moving this off the admin port if §7's admin-disarm row is ever tightened
- [x] **Deployment key rotation ≤24h with 2-key overlap** (NFR-5) — landed 2026-08-16, `internal/tis/keyring.go`. Sign with current, verify with either, `kid` in the JWT header selecting which — the same 8-byte SHA-256-of-PKIX construction the ledger has stamped since v0.8.5, reused verbatim rather than reinvented so no existing evidence is re-labelled. **The overlap is one full interval, so exactly two keys are ever live**: the previous key is retired when the next rotation displaces it, not on a second timer, because two clocks deciding when a key dies is how a deployment ends up verifying against a key it has already forgotten. `TestOverlapOutlivesToken` pins the constant relationship — the window must exceed `MaxTxnTTL` or a token can be born already doomed, valid when issued and unverifiable before its own expiry. **Both keys persist** (`tis-key.pem`, `tis-key.prev.pem`): a restart inside the window that forgot the previous key would fail every token minted before the rotation, which is D2's hazard one key over, and NFR-3 makes it degrade the evidence silently rather than stop. **Trigger is timer + `POST /keys/rotate`** (author decision 2026-08-16): automatic, because a key that rotates when someone remembers is not the guarantee NFR-5 states, plus a manual path for compromise and for §8.3's rotation-under-live-traffic drill. The retention precedent (manual only) deliberately does *not* carry over — pruning destroys evidence, rotating destroys nothing. Closes D12's named ceiling: cached auto-minted tokens carry the key generation, so a rotation invalidates them
- [ ] **Ledger signing key rotation** — deliberately **not** in the above, and separated from it on 2026-08-16 rather than half-built. The two keys have nothing in common but the word: `ledger.Open` refuses to resume a chain under a different key and the verifier rejects a `kid` change *within* a file, both on purpose, so rotating it means sealing and rolling every open segment (D14's roller already does this) and then teaching `gurdy-verify` to walk a chain across a key change. It also changes what a third party must be handed — `-pubkey` pins exactly one key, and a rotated export needs a keyset. This is the "verifier must handle multi-key periods" half of NFR-5

### C. Ledger and record completeness

- [x] Wire real partitions (D3)

### G. Performance gates (wk 10–12)

**Full findings and methodology: `docs/performance.md`.** `cmd/gurdy-bench` is the offline harness (open-loop, A/B/A, refuses to subtract percentiles, reads the ledger's drop counters); `internal/clock` is the live one, served at `GET /latency`; microbenchmarks live in `cmd/gurdy-proxy/bench_test.go`.

- [x] **Live latency clocking** — `internal/clock`, ~100ns per observation and zero allocations, so there is no flag to disable it. Per stage of the §4.2 loop, percentiles rather than averages (a mean would have hidden every defect found here), served at `GET /latency` with `DELETE /latency` to start a fresh window. The payload states what it excludes — the hop, which is the larger term of NFR-1's budget — because a reader who takes `decide p99` for the gate figure has been misled by us

- [x] **Microbench: derive / eval / extract each <1ms.** Measured on an M3 Pro: eval 922ns, extract 158ns, derive+verify 124µs, whole in-process decision 223µs. **Identity is 77% of the decision path** (172µs of 223µs) — three ES256 operations per call — and extract+eval together are under 0.5% of it. Any future latency work belongs in the crypto, not the policy engine
- [x] **Measure D5 (body buffering) explicitly.** Not the culprit the roadmap suspected: +9µs at a 64 KiB frame, negligible against 223µs of identity work. It only bites at the cap — **+1.65ms at 4 MB**, a third of the p50 budget. Realistic MCP frames are kilobytes, so D5 is debt with a known ceiling rather than a defect
- [x] **Throughput: 6,000 decisions/sec with zero dropped records**, 6× NFR-2's 1,000/s, sustained 60s at 3,000/s (180k requests per arm, zero drops, zero write errors). Added p50 is **217–265µs**, stable across every run and corroborating the microbenchmark
- [x] **Sustained 30-minute run at 1k/sec** — ran 2026-08-08, `gurdy-bench -soak`. **1.8M requests, schedule held at 1,000/s in every one of 30 windows, zero dropped records, zero write errors, zero identity failures.** Latency did not creep: p50 **753µs → 761µs (+1.1%)**, p99 **995µs → 998µs (+0.3%)** first window to last. Memory rose 16.5 MB → 46.9 MB but **decelerating toward a plateau** (+32 KB/min at minutes 15–20, +6 KB/min at 25–30) — steady state, not a leak; note D6's unbounded `autoTxn` map could not show here, since all load came from one client IP. File descriptors held 44–82 with no trend. **The one real finding is D14**: the export grew 1.9 GB in 30 minutes with no rotation. Soak mode reports rather than gates, deliberately — the thresholds worth gating on are what this run establishes, and a gate invented before the first measurement is a guess wearing a number's clothes
- [x] **Our own share of the p99 budget is measured: ~300µs, or 6% of it.** `TestDecisionServiceTimeDistribution` times `decideCall` in-process on a monotonic clock, so the tail is attributable rather than swamped by the loopback stack. Five repeats: p50 **179–183µs**, p99 **284–361µs**, p99.9 606µs–1.33ms. Under full 12-core saturation (≈48k decisions/sec offered, 48× NFR-2) p99 is still only **1.55ms**. This is the half of NFR-1 that does not need a deployment, and it splits the budget cleanly: `hop + derive + extract + eval ≤ 5ms`, where everything after `hop` is now a known 300µs
- [x] **The rare outlier is the OS, not us, and not GC.** Max ranges 1.8–17.3ms run to run. The obvious suspect was garbage collection — 32KB and 398 allocations per decision — but `GOGC=off` produced the *worst* max of all (17.3ms), so it is scheduler preemption on a shared machine. Recorded because the wrong explanation would have sent someone optimising allocations for no gain
- [ ] **Composed p99 (the hop): NOT RESOLVABLE on a laptop, and the harness says so rather than guessing.** The ungoverned baseline's own p99 swings between 1.6ms and 14ms and its p999 reaches 93ms, against a 5ms budget for the *added* cost — the effect is smaller than the ruler's markings. NFR-1 gates a deployed sidecar; it has to be measured on a quiet dedicated host, which is the remaining work here. A related artifact worth knowing: at 1,000/s the 1ms inter-arrival gap sits at the platform's timer resolution, so the tail is *worse* at 1,000/s (10.5ms) than at 3,000/s (896µs) — that is the clock, not a load response
- [x] **Fan-out burst: 20 sub-agents × 50 concurrent calls, correct lineage on every record** — landed 2026-08-07, `cmd/gurdy-proxy/fanout_test.go`. 1,000 calls released from one gate; **1,000 decision records checked, zero dropped**, so the bounded queue absorbs an instantaneous 1,000-call burst without shedding evidence. Lineage held on every record. **Self-consistency was not the assertion** — a record whose `lineage[1]` and `asserted_principal` agree can still be attached to another agent's call and look right both ways — so each agent calls a tool named after itself and the test asserts the *wire* (tool) and the *credential* (lineage) agree, which they can only do if nothing crossed. Mutation-checked by having each agent send the next agent's credential: fails with `agent-19: lineage does not match the caller: [orchestrator agent-00]`. **It found a data race on its first run under `-race`** — in `newHarness`, not the proxy: the upstream stub's `saw`/`sawHdr` were written unguarded by every handler goroutine, latent because every other test sends one request at a time. Fixed; a harness that races is a harness whose failures get blamed on the code under test

**Two defects found, both invisible to a microbenchmark of the decision path, which is precisely why §8.2 forbids certifying NFR-1 by summing them:**

| Defect | Effect |
|---|---|
| `httputil.NewSingleHostReverseProxy` inherited `http.DefaultTransport`, whose `MaxIdleConnsPerHost` is **2**. A sidecar talks to one upstream, so that was the entire pool — past two concurrent calls every request dialled fresh TCP and left the old connection in TIME_WAIT | fixed: `maxUpstreamConns = 256` |
| The decision log wrote synchronously to stdout **per decision**, serialised behind slog's handler mutex | fixed: `flushWriter`, 5,311ns → 392ns per record under parallel load (13.6×) |

### H. Adversarial corpus v1 (wk 8–12) — ≥25 traces

- [x] **v1 landed 2026-07-26: 26 traces, 19 defences pinned, 7 gaps documented** (`corpus/traces`, `corpus/README.md`). Runs in CI. Shares the conformance runner rather than forking it — a trace is a conformance case asking "did the pack reach the right verdict?" instead of "did the SDK produce the right evidence?", and a forked judge is a judge that drifts. All `kind: wire`: an attacker does not politely use your SDK.
- **Three outcomes, not two.** PASS, GAP (the attack succeeds today — the trace asserts what actually happens, says why, and names what closes it), FAIL. The summary reads *"N documented gaps — attacks this pack does NOT stop"* so a green run cannot be skimmed as more than it says. **A gap that no longer reproduces is a FAILURE**, which is what stops `known_gap` becoming a graveyard; it fired on the first run and caught a gap I had asserted that did not exist.
- [x] **First gap closed by the corpus that found it.** `resource_path` was matched case-sensitively while `context.tool` was folded, so `/home/u/.SSH/id_rsa` bypassed the flagship BR-11 credential control on any case-insensitive filesystem. Case folding is now a property of *matching* rather than of one field — every string a policy compares is folded, the ledger keeps the raw value — because the bug was not that one field was forgotten, it was that the rule lived in one place instead of at the boundary. Closing it turned trace 05 red with "this known gap NO LONGER REPRODUCES"; it is now a PASS, plus trace 26 varying case across the whole path, since a repair that special-cased `.ssh` would pass one and fail the other
- **The seven remaining gaps, and what they say.** Five share one root cause — controls match on strings the governed party chooses (tool name, argument name) — the §7 aliasing problem and the case for tool-signature binding in §3.D, whose *case* dimension is now closed. The other two are missing controls: **no spend policy** (BR-11 advertises three protections and ships two) and **no rate control**. One more is narrower: model calls to a loopback endpoint are exempt from the unlisted-host rule, so a local relay collects traffic unflagged.
- [ ] **Traces gain an expected *action*** when the Phase 2 actuator lands. Today every trace ends `forwarded`, including the ones whose attack was detected, so "the corpus passes" means every attack produced the right verdict — not that any was stopped
- [ ] Grow past 25 as the packs deepen; vertical packs ship their own corpus (FHIR compartment escape, `$export` smuggling)
- **Deliberately not in the corpus:** evidence-integrity attacks (forged unsigned tail, non-canonical base64 signature, cross-replica replay) stay as Go tests, where a test can corrupt a specific byte and assert the exact error. Two harness limits are stated in `corpus/README.md` rather than papered over: a loopback upstream cannot reach the unlisted-egress branch, and one proxy instance cannot reach cross-replica replay.

- [x] **npm Trusted Publishing — no token at all, matching PyPI** (2026-08-07). The `@gurdy` org was created, and the token minted for it is already obsolete: all six packages (`@gurdy/cli`, four `@gurdy/cli-<os>-<arch>`, `@gurdy/sdk`) now trust `GurdyAI/gurdy` + workflow `release.yml`, environment blank. **Environment deliberately blank** — the publish gate is already the `release: published` event, and a name in a web UI that must stay in sync with a workflow file is the "repo setting somebody has to remember" that gate was chosen to avoid. **`publish` only, not `stage publish`** — granting both protects nothing, since an attacker controlling the workflow just picks the weaker one; stage-only is the real upgrade and its trigger is the day someone outside the two of us can land a change reaching `release.yml`. Getting there needed a **placeholder publish**: npm cannot do a first-ever publish over OIDC ([npm/cli#8544](https://github.com/npm/cli/issues/8544)), so six `0.0.0` stubs went up under the `placeholder` dist-tag. **The claim originally made for that dist-tag was wrong, and is corrected here rather than quietly dropped** (found 2026-08-11 while pre-flighting the first tag): it said the stubs went up "under `placeholder` rather than `latest`", so a premature `npm i -g @gurdy/cli` would fail loudly instead of installing a no-op. npm sets `latest` on a package's **first** publish regardless of `--tag`, so all six read `latest → 0.0.0` from the moment they were created, and the protection never existed. What a premature install actually does is *succeed*: the stub declares no `bin`, so nothing errors and the user is left with no `gurdy` command, discovering it at first use as `command not found`. Only the package description says "Placeholder — not a release", and only to someone who looks. **Publishing v0.1.0 moves `latest` and closes it**; the window was 2026-08-07 to the first published release, against packages nobody had been told existed yet. Recorded because the mistake is a class worth recognising — a protection asserted from what a flag *should* mean, never checked against the registry afterwards, and the check is one `npm view` away
- [x] **Repo/account prerequisites — all closed 2026-08-11.** ~~npm `@gurdy` org + `NPM_TOKEN`~~ done, and the token is obsolete (above); PyPI `gurdy` with Trusted Publishing, no token; and now `GurdyAI/homebrew-tap` (public, `main`, README pushed so GoReleaser has a default branch to publish `Casks/gurdy.rb` into — `.goreleaser.yaml` pins no `branch:`, so it follows the default) plus `HOMEBREW_TAP_TOKEN`. That token is the **only long-lived credential in the entire release path**, and only because a git push to another repository has no OIDC equivalent — cosign, npm and PyPI all authenticate without one. It is fine-grained, scoped to `homebrew-tap` alone with `Contents: read and write` and nothing else, which is what keeps a leak at "someone rewrites generated packaging metadata" rather than "someone publishes a Gurdy release". A classic PAT was the easier path and was **not** taken: its narrowest workable scope is `public_repo`, which grants write to every public repo on the account including `GurdyAI/gurdy` itself. **Untested until the first tag, by construction** — the cask push runs inside the `release` job and there is no way to exercise a repository secret without a run. The blast radius is small on purpose: GoReleaser cuts a **draft** release, and `publish-npm`/`publish-pypi` fire on `release: published`, so a bad token fails the tag with artifacts uploaded and nothing distributed. Re-run after fixing rather than untangling a half-published release
- [ ] install-to-first-decision ≤5 min timed in CI per channel — needs a published release to time against
- [ ] **macOS notarization deliberately skipped** (no Apple Developer account, author decision 2026-07-26). brew is the documented macOS path; the curl path clears quarantine itself. Notarization is a seam in the release workflow, not a rewrite, if that changes

**Phase 1 exit:** stranger-run 15-minute demo, no author present, plus full CI green.

## 4. Phase 2 — partner deployments + local enforcement

Phase 2 is the phase that grew under ADR-14.

**Enforcement workstream (new, free tier):**

- [x] **Actuator interface** — landed 2026-07-25 (`cmd/gurdy-proxy/actuator.go`). One implementation (`monitorActuator`, forwards everything, ADR-3), deliberately behind an interface: the second implementation is this phase's work, every transport must consult it, and without the seam adding blocking meant editing both transports and the decision path at once. `Plan.Durable` names the §5.5 record-before-effect ordering so it can be enforced at the seam rather than in each transport
- [ ] **Local block actuator, HTTP path** — short-circuit the reverse proxy, synthesize a protocol-level error
- [ ] **Local block actuator, stdio shim** — harder: `relay()` is a pure forwarder. Blocking means writing a JSON-RPC error to stdout without forwarding to the child, preserving framing
- [ ] **Batch semantics** (§5.1, normative): a blocked call becomes an error element; siblings evaluate and forward independently
- [ ] Per-policy `enforce_action` / `on_error` honored (`on_error` is validated but not stored today); `fail_mode_applied` populated with what the actuator actually did. **Require both annotations on every `forbid` here** — the value vocabulary is checked at load already, but a misspelled *key* is indistinguishable from an absent one, which is harmless while the defaults match monitor behavior and is a silent non-block the moment it isn't
- [ ] Fail-open default on single-instance installs, verified by a kill-under-load drill (FR-11)
- [ ] **Shadow-mode diff tooling** — "would have blocked." Ships *before* any policy may graduate
- [ ] **Enforcement record durability.** The ledger queue is async and drops on overflow — correct for monitor (a dropped observation is a counted coverage gap), **wrong for a block**. Blocking with no record, or failing open with no record, produces exactly the unattributable action this product exists to eliminate. Enforced-path records write synchronously before the actuator's effect is released
- [ ] **Admin-API disarm (§7, security).** The admin API is localhost-bound with a CSRF guard — which stops a browser, not a process already on the box, and the governed agent always is. A prompt-injected agent can `POST /policy/rollback` and delete the policy that would block it. Under monitor that's log integrity; under local enforce it's a total bypass. Needs token auth on mutating routes + every bundle change recorded in the ledger
- [ ] **Local bypass story.** A laptop has no NetworkPolicy — the cluster answer to "route around the proxy" doesn't exist here. Install-time MCP client config rewriting, plus coverage detection that makes an un-proxied path visible. Weaker than the cluster story; document it honestly rather than implying a laptop is sealed
- [ ] **Agent-framework retry behavior.** A blocked JSON-RPC error may send a real agent into an infinite retry loop. Test against actual LangChain / Claude agent SDK / MCP TS clients — protocol correctness is not agent-loop correctness
- [ ] **Recovery UX** — "why was this blocked", temporary monitor override, safe mode, policy rollback. The false-positive path is the one a free-tier user hits before they uninstall
- [ ] **Starter-policy update/revocation channel.** Once free starter policies can block, a bad policy is a live incident on other people's machines. Needs signed policy rollback and a security-advisory path
- [ ] Enforce-path p99 re-measured against NFR-1, now a free-tier release gate
- [ ] Corpus traces gain expected actions
- [ ] Reporter/dashboard absorb blocking: blocked-vs-flagged, `policy_mode` history, fail-open/closed events, retry-loop patterns, per-policy rollout state
- [ ] **OQ #13** — free-tier blast radius: blocking policies off by default vs. a curated always-safe subset. Settle before enforce ships

**Existing Phase 2 content:** partner deployment (AKS/EKS/OpenShift), evidence-integrity drills (mutation, clock-skew, restart-gap), tap-mode mirror fidelity ≥99.5%, key rotation under live traffic, Helm/Compose, native Windows, orphan+indeterminate <5% by day 60, full framework-mapped reporter, SOC 2 paperwork starts, IRB posture closed (OQ #5).
